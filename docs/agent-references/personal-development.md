# 个人开发规范

本文档记录个人开发过程中形成的补充规范。

团队公共规范优先适用于所有项目；本文档用于补充个人在需求开发、接口调用和 Agent 协作过程中的具体要求。

本规范可以持续更新。后续发现新的高频问题、重复错误或稳定实践时，应及时补充。

## 1. 接口调用规范

### 1.1 查询类接口

在 React 组件或自定义 Hook 中调用接口时，必须优先使用 ahooks 的 `useRequest`。

不得自行维护一套重复的请求状态，例如：

```tsx
const [loading, setLoading] = useState(false);
const [data, setData] = useState<Data>();
const [error, setError] = useState<Error>();
```

不推荐在组件中手动编写以下重复逻辑：

```tsx
setLoading(true);

try {
  const result = await requestData();
  setData(result);
} catch (error) {
  setError(error);
} finally {
  setLoading(false);
}
```

推荐使用：

```tsx
const { data, loading, error, run, refresh } = useRequest(getData, {
  manual: true,
});
```

使用 `useRequest` 统一管理：

- 请求状态
- 返回数据
- 返回数据的格式化（formatResult）
- 错误状态
- 手动触发
- 重新请求
- 请求取消
- 防抖和节流
- 轮询
- 依赖刷新

除非 `useRequest` 明确不适用于当前场景，否则不得自行重复实现请求状态管理。

### 1.2 操作类接口

新增、修改、删除、发布、停用、提交、保存等操作类接口，同样应使用 `useRequest`。

操作由按钮触发时，必须将请求的 `loading` 状态传递给对应按钮：

```tsx
const { runAsync: handleSave, loading: saveLoading } = useRequest(saveData, {
  manual: true,
});

<Button loading={saveLoading} onClick={handleSave}>
  保存
</Button>;
```

必须通过按钮 Loading 或禁用状态避免以下问题：

- 用户连续点击
- 重复提交
- 重复创建数据
- 重复发送请求
- 请求未结束时再次执行相同操作

不得只依赖用户不会连续点击。

### 1.3 操作状态对应原则

不同操作应使用各自独立的 Loading 状态。

例如页面同时存在保存、发布和删除操作时，不应共用一个通用 `loading`：

```tsx
const { loading: saveLoading } = useRequest(saveData, {
  manual: true,
});

const { loading: publishLoading } = useRequest(publishData, {
  manual: true,
});

const { loading: deleteLoading } = useRequest(deleteData, {
  manual: true,
});
```

每个 Loading 状态只控制对应的触发位置，避免一个接口请求导致无关按钮同时进入 Loading 状态。

## 2. 需求依据优先级

当产品文档、接口文档和 UI 视觉稿之间存在差异时，按以下优先级判断：

```text
产品文档 > 接口文档 > UI 视觉稿
```

### 2.1 产品文档

产品文档是业务逻辑和验收标准的最高依据。

主要用于确认：

- 功能范围
- 业务流程
- 字段含义
- 状态规则
- 操作权限
- 交互限制
- 异常处理
- 验收标准

测试用例通常根据产品文档编写，因此不得仅根据接口文档推断业务规则。

### 2.2 接口文档

接口文档用于确认：

- 请求地址
- 请求方式
- 请求参数
- 响应字段
- 字段类型
- 枚举值
- 分页结构
- 异常码

接口文档只能决定前后端数据交互方式，不能覆盖产品文档中的业务规则。

如果接口实现与产品文档不一致，应先明确差异，不得直接以接口当前行为替代产品需求。

### 2.3 UI 视觉稿

UI 视觉稿主要用于确认：

- 页面布局
- 尺寸
- 间距
- 颜色
- 字号
- 对齐方式
- 组件形态
- 页面状态展示

视觉稿不能单独决定业务逻辑。

如果视觉稿缺少某个业务状态，应结合产品文档补充，而不是认为该状态不存在。

### 2.4 文档冲突处理

发现文档存在冲突时，不得自行选择更容易实现的一方。

应明确列出：

```text
冲突位置：
产品文档：
接口文档：
UI 视觉稿：
当前建议：
待确认事项：
```

在未确认前，可以基于产品文档实现，但必须保留明确记录，避免后续因认知差异产生返工。

## 3. Agent 错题本机制

项目中应维护独立的 Agent 错题本：

```text
docs/agent-references/agent-mistakes.md
```

### 3.1 记录条件

同一个错误被 Agent 连续出现两次时，必须记录到错题本。

包括但不限于：

- 相同布局问题重复出现
- 相同组件使用方式重复出错
- 相同业务规则被重复误解
- 修改一个问题时重复破坏其他功能
- 已明确要求的规范仍被再次违反
- 已修复的问题在后续修改中再次出现
- Agent 两次采用错误的实现路径
- Agent 两次忽略已有项目实现

第一次出错时正常修复。

第二次出现相同或高度相似的错误时，必须：

1. 分析错误根因。
2. 记录错误表现。
3. 记录正确做法。
4. 记录后续检查方式。
5. 在相关任务开始前读取该条记录。

### 3.2 错题记录格式

```md
## [日期] 错误标题

### 错误表现

描述 Agent 实际产生的问题。

### 出现次数

2 次。

### 错误原因

说明是因为遗漏规范、错误理解需求、未检查现有代码，还是修改范围失控。

### 正确做法

记录后续应采用的实现方式。

### 检查方式

说明以后如何在开发或交付前发现该问题。

### 关联文件

- `src/...`
- `docs/...`
```

### 3.3 使用要求

开始开发前，如果任务涉及已有错题，应先阅读对应记录。

完成开发后，应检查本次修改是否再次触发错题中的问题。

错题本不是过程流水账，只记录：

- 重复发生的问题
- 影响较大的问题
- 有明确复用价值的经验
- 可以转化为后续约束的问题

如果某条错误已经形成稳定规则，可以将其提升到对应规范文件中，并在错题本中保留来源记录。

## 4. 规范更新原则

本文档采用持续补充方式维护。

新增规范时，应满足以下条件之一：

- 同类问题出现多次
- 已形成稳定开发习惯
- 可以明显减少返工
- 可以避免常见线上或测试问题
- 对 Agent 开发行为有明确约束价值

不得将临时需求或单个项目的特殊逻辑写入通用个人规范。

项目特有规则应放在项目自己的文档中。

## 5. 待补充

后续开发过程中发现新的个人规范时，继续在本文档补充。

建议优先记录以下类型：

- 接口调用习惯
- 表格开发习惯
- 页面布局要求
- Mock 数据要求
- 提交前检查流程
- Agent 修改边界
- 需求理解和验收规则
