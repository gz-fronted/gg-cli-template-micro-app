# Agent 开发工作流

本文约束 Agent 在业务项目中的协作方式、修改边界、验证过程和经验沉淀。产品、接口和
UI 的依据优先级统一见 `requirements.md`，接口调用细节见 `api.md` 和 `gz-fetch.md`。

## 开始任务

1. 阅读 `index.md`，再按任务类型加载直接相关的规范。
2. 检查工作区状态和现有实现，识别用户已有且与任务无关的改动。
3. 从产品、接口和设计资料中提取本次任务的业务边界与验收项。
4. 发现资料冲突时明确列出差异、当前建议和待确认事项，不选择更容易实现的一方。
5. 在现有信息足够且修改范围明确时直接推进，不把机械性工作转交给开发者。

## 修改边界

- 只修改完成当前需求所需的文件和配置。
- 保留已有且无关的用户改动；无法安全绕开冲突时再请求方向。
- 不借业务需求顺带迁移依赖、重构脚手架、替换组件库或改写公共基础设施。
- 不为了通过类型、Lint 或构建而隐藏问题、扩大 ignore、滥用断言或使用 `any`。
- 可复用规则进入对应规范或 Skill；单个页面的临时实现不进入团队通用规范。

## 实现和验证

- 功能开发同步考虑 loading、空数据、错误、禁用、重复提交和权限等已定义状态。
- UI 开发必须运行页面核对尺寸、间距、滚动、组件状态和设计偏差。
- 修复滚动、虚拟列表、固定列或浮层问题时，必须覆盖初始状态及往返操作后的状态。
- 根据改动范围执行 `code-quality.md` 中的检查；不得把“代码能编译”当作完整验收。
- 未执行的检查必须说明原因，不得声称未实际运行的验证已通过。

## 错题本机制

项目错题本位于：

```text
docs/agent-references/agent-mistakes.md
```

同一个或高度相似的错误重复出现两次，或一次错误造成较大影响并具有明确复用价值时，
必须记录。第一次普通修复不自动写入。

记录格式：

```md
## [日期] 错误标题

### 错误表现

### 出现次数

### 错误原因

### 正确做法

### 检查方式

### 关联文件
```

开始相关任务前读取已有记录，完成后确认没有再次触发。错题形成稳定通用规则后，将规则
提升到对应规范或 Skill；错题本保留问题来源，不复制整篇规范。

## 规范更新原则

新增或提升规则应至少满足一项：

- 同类问题重复出现。
- 已形成稳定且可跨业务复用的实践。
- 能显著降低返工、线上风险或测试遗漏。
- 对 Agent 的选择和验证行为有明确约束价值。

项目业务枚举、页面文案、具体接口字段和一次性视觉特例不得写入通用模板。
